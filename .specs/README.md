# Specifications and tasks

Start with [the issue #1 plan](PLAN.md), then [the feature spec](tasks/todo/issue-1-hashpass-commerce/00-SPEC.md). The [issue snapshot](ISSUE-1.md) preserves the source requirements. MVP-01 is the first internal delivery task; external commercial validation is a later evidence gate.

## Workspace

```text
.specs/
  tasks/draft/                  # unanalysed work, excluded from package discovery
  tasks/todo/<feature>/         # planned tasks and 00-SPEC.md
  tasks/in-progress/<feature>/  # active work
  tasks/done/<feature>/         # completed tasks with evidence
  .agents/pending-tasks -> ../tasks/todo
  .agents/active-tasks  -> ../tasks/in-progress
  .agents/done-tasks    -> ../tasks/done
  .versioning/                  # generated reentry snapshot
  scratchpad/                   # ignored temporary notes
  versioning.config.json
```

Task bodies and `00-SPEC.md` are canonical; indexes and reentry files are generated. Stable `MVP-XX`/`HP-XX` IDs identify dependencies across moves. MVP tasks prove internal capabilities first; HP-01 and later external tasks collect evidence that code alone cannot provide. Keep the feature spec in todo until the epic is complete. Do not copy it into each lifecycle folder.

## Verified package integration

Inspected the npm-published `@edcalderon/versioning@1.5.13` tarball on October 10, 2026: [package](https://www.npmjs.com/package/@edcalderon/versioning), [upstream source](https://github.com/edcalderon/my-second-brain/tree/main/packages/versioning). Its task scanner hardcodes `.agents/{active,pending,done}-tasks/<feature>/*.md`; it identifies exactly `00-SPEC.md` as the spec and requires Goal, Tasks and Acceptance Criteria headings. It cannot configure `.specs` as its task root.

Run it with `.specs` as cwd and category-directory symlinks to the real task folders. This keeps one record per task and avoids modifying the repository-root `.agents` directory. Symlinks must be preserved by checkout. The config uses root-level `reentryStatus`: this matches the inspected tasks validator's `cfg.reentryStatus.files` access in 1.5.13.

```sh
pnpm specs:list
pnpm specs:sync
pnpm specs:validate
# Pass extra filters after the script name:
pnpm specs:list --status pending --json
```

Commands pin the top-level CLI version through pnpm dlx; first use needs registry access. Its transitive dependencies are resolved by dlx, not the app lockfile. Only task commands are exposed; the config is not a release workflow. No package lifecycle hook is added to this repository.

## Task lifecycle

1. Add unanalysed work under `tasks/draft`. Flesh out scope, dependencies, steps, affected paths, acceptance and evidence before promotion.
2. Move ready work into `tasks/todo/<feature>`. Set `Status: pending`; do not confuse planned with implemented.
3. Check prerequisite evidence, then move a selected file to `tasks/in-progress/<feature>` and set `Status: active`. Maintain its stable ID.
4. Record PR/commit, meaningful checks and scrubbed exit evidence; check acceptance boxes only when proven.
5. Archive with the verified package command (path relative to the `.specs` workspace):

```sh
cd .specs
pnpm dlx @edcalderon/versioning@1.5.13 tasks archive .agents/active-tasks/<feature>/<task>.md
```

6. Run sync and validate after every edit/move; update PLAN.md links if a task moves. Generated feature README indexes are regenerated by sync. Package validation checks indexes/spec headings/snapshot consistency; it does not enforce dependency gates or prove business/security acceptance.

To create a template using the package, from `.specs`:

```sh
pnpm dlx @edcalderon/versioning@1.5.13 tasks add .agents/pending-tasks/<feature>/<task>.md --status pending --title "Add specific behavior"
```

Do not send outreach or broadcast funds merely because a task exists. Follow the task's actual authorization/evidence gates. Keep keys, cookies, private customer/financial records, raw signing journals, screenshots and recordings outside tracked documentation.
